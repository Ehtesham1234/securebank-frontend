# SecureBank — Frontend

Angular frontend for the SecureBank microservices backend (eureka-server,
api-gateway, securebank-api, account-service, kyc-service, loan-service,
notification-service, ai-service).

**Status: Phase 2 — Account security.** Everything from Phase 1 (auth +
shell) plus session management: viewing active sessions, revoking a session,
and logging out of every device. Accounts, cards, transfers, loans, KYC, the
AI assistant, and the admin/teller consoles are **not** built yet — see
"Roadmap" below.

## Stack

- Angular 18, standalone components, Signals for state (no NgRx)
- Tailwind CSS 3 + PrimeNG 18 (Aura theme, customized — see "Design system")
- `jwt-decode` for reading the access token's claims client-side
- `@stomp/stompjs` + `sockjs-client` are installed and ready for the
  real-time balance feed (`/ws`), but nothing subscribes yet — that lands
  with the accounts feature in a later phase

## Prerequisites

- Node.js 20.x (Angular 18 needs Node ^18.19 or ^20.11+)
- The backend running via `docker-compose-microservices.yml`, with
  `api-gateway` reachable at `http://localhost:8090`

## Setup

```bash
npm install
```

This project was generated by hand (file by file), **not** via `ng new` —
if `npm install` reports a peer-dependency mismatch, it's most likely a
patch-version drift in `primeng` / `@primeng/themes` / `tailwindcss-primeui`;
bumping to the latest compatible patch within the same major version should
resolve it.

Then either:

```bash
# Option A — talk to the gateway directly (relies on the gateway's CORS
# allow-list, which already includes localhost:4200)
npm start

# Option B — proxy through the dev server instead, sidestepping CORS
# entirely (see proxy.conf.json)
npm run start:proxy
```

Both serve on `http://localhost:4200`.

## Environment configuration

`src/environments/environment.ts` (dev) and `environment.prod.ts`
(production build) hold `apiBaseUrl` and `wsUrl`. Every HTTP call in the app
goes through **one** base URL — the api-gateway — never a downstream
service directly. Update `environment.prod.ts` before shipping; it still
points at `localhost` as written.

### State management

No NgRx. `AuthService` exposes the session as a `signal<CurrentUser | null>`
plus a `computed` `isAuthenticated`. Feature services added in later phases
should follow the same shape: an injectable service owning its own signals,
exposing `computed` selectors, with components reading signals directly in
templates. This keeps each feature's state colocated with the HTTP calls
that populate it instead of a separate store layer.

### Auth & token handling

- **Access token**: kept only in memory (a signal in `TokenStorageService`).
  Never written to `localStorage`, to shrink the XSS blast radius. Cost: a
  hard reload loses it, which is why `AuthService.initFromStorage()` runs a
  silent refresh via `APP_INITIALIZER` before the router activates any
  guarded route.
- **Refresh token**: persisted in `localStorage` so a session survives a
  reload. This is a real trade-off (a stored refresh token is readable by
  injected script) — it's necessary because the backend returns both tokens
  in the JSON response body rather than an httpOnly cookie. If that changes
  backend-side, `TokenStorageService` is the only file that needs to change.
- **401 handling**: `authInterceptor` attaches the bearer token, and on a
  401 (for any request that isn't itself an auth endpoint) does a
  single-flight silent refresh — concurrent 401s share one refresh call —
  then retries the original request. If the refresh itself fails, the
  session is cleared and the user is sent to `/auth/login`.
- **Interceptor order matters**: `[errorInterceptor, idempotencyInterceptor,
  authInterceptor]`. `authInterceptor` is closest to the actual request, so
  it gets first crack at a 401 and can resolve it silently; `errorInterceptor`
  only shows a toast for whatever `authInterceptor` couldn't resolve.

### Account security

Three endpoints, all under `/account-security` on securebank-api (properly
role-scoped with `@PreAuthorize`, unlike some of the account/loan-service
admin endpoints noted above): list active sessions, revoke one, log out
everywhere. A few deliberate choices:

- The backend returns no device/browser/IP info — just a session's
  `tokenFamily` and its timestamps. The UI shows that honestly (a truncated
  token family in the ledger font, full value on hover) rather than
  fabricating "Chrome on Windows"-style device labels that aren't backed by
  real data.
- **Revoking your own current session is disabled in the UI**, not just
  discouraged. The backend would probably allow it, but revoking the
  session you're actively using mid-request leaves the access token in
  memory valid until it next tries to refresh — a confusing half-logged-out
  state. Use the topbar's "Log out" for that instead.
- **Logout-all-devices also ends the current session** (it revokes every
  refresh token for the user, this one included), so the component clears
  local state and redirects to `/auth/login` on success via
  `AuthService.clearLocalSession()` — a new method that clears local state
  without hitting `/auth/logout` again, since the server-side revocation
  already happened through the other endpoint.

### Backend contract quirks the UI is built around

These aren't bugs in the frontend — they're deliberate backend behavior
worth knowing before you extend this:

- **Login is blocked until email is verified.** `AuthServiceImpl` throws
  `EmailNotVerifiedException` (403, code `EMAIL_NOT_VERIFIED`) at login, not
  at registration. `LoginComponent` catches this specifically and redirects
  to `/auth/verify-email`.
- **Registration and forgot-password never reveal whether an email
  exists** (anti-enumeration, by design in `AuthServiceImpl`). Both always
  return the same success shape. Don't "improve" the UI copy to
  differentiate these cases — that would defeat the point.
- **No display name after login.** The JWT only carries `sub` (email),
  `role`, `userId`, `userStatus` — no first/last name — and there's no
  `GET /me` endpoint routed through the gateway. The UI shows the email as
  the identity string. If you add a profile endpoint later, wire it into
  `AuthService` and update the topbar.
- **`UserStatus` is effectively `PENDING_KYC | ACTIVE` post-login** —
  `SUSPENDED`/`CLOSED` users are rejected at login before a token is ever
  issued, so the shell's status handling doesn't need to branch on those.

### Things worth fixing on the backend before you build further

Found during the API audit, not introduced by this frontend:

1. **`account-service`'s and `loan-service`'s `/admin/**` endpoints have no
   `@PreAuthorize`** — only "authenticated", not "authenticated AND ADMIN",
   is enforced at the Spring Security layer. `roleGuard` in this app hides
   the UI for non-admins, but that's a client-side convenience, not a
   security boundary — a CUSTOMER's token can currently call these
   endpoints directly.
2. **The loan-service `pay-emi` endpoint requires an `X-Account-Id`
   header**, but the gateway's CORS `allowedHeaders` list doesn't include
   it (see `ApiGatewayApplication`'s CORS config) — a browser preflight for
   that call will fail as written. This isn't hypothetical: even the
   project's own Postman collection's "Pay EMI" request doesn't send
   `X-Account-Id` either (it only sends `Idempotency-Key`), so it would 400
   on the missing-header check if run as-is. Easiest fix is probably moving
   `accountId` into the request body instead of a header — sidesteps the
   CORS allow-list issue too.

## Design system

- **Body/UI**: IBM Plex Sans. **Headings on auth screens only**: Fraunces
  (a serif, used narrowly — never for dense dashboard UI). **Every currency
  amount, account/card number, and OTP digit**: IBM Plex Mono with tabular
  figures (`.font-ledger` utility) — the one consistent signature carried
  through every screen, so columns of numbers actually align.
- **Color**: brand primary is "Vault Teal" (PrimeNG's `teal` semantic scale,
  see `core/theme/securebank-preset.ts`) — deliberately not the generic bank
  blue. A muted antique-gold (`gold-*` in `tailwind.config.js`) is the one
  accent color, used sparingly (active-nav indicator, the auth-layout side
  panel, verified badges) — never for large surfaces or body text.
- **Signature element**: the auth-layout's side panel has a slow, looping
  "ledger tape" — illustrative transaction rows, not real data — which
  respects `prefers-reduced-motion` (see the global media query in
  `styles.scss`).

## KYC module (customer submission + status, teller review)

Lives under `features/kyc/` (customer) and `features/teller-kyc/` (staff).

- **`KycService`** (`features/kyc/kyc.service.ts`) — signal-based status state
  (`status`/`loading`/`checked`), same shape as `AccountSecurityService`.
  `GET /kyc/status` 404s when nothing's been submitted yet — that's treated
  as a normal state (`status` set to `null`), not an error, using a new
  `withSilentErrors()` escape hatch on the error interceptor (see below) so
  no toast fires for it.
- **`KycComponent`** (`features/kyc/kyc.component.ts`) — the `/kyc` route.
  A thin container that swaps between the submit form and the status view
  based on `KycService`'s signals, and — via an `effect()` — calls
  `AuthService.refreshAccessToken()` the moment it sees `status: 'VERIFIED'`.
  This matters: the backend flips a customer from `PENDING_KYC` to `ACTIVE`
  in the database on verification, but `userStatus` is baked into the JWT at
  issue time, so the browser's *existing* token is stale until refreshed —
  without this, the UI would look stuck even though verification succeeded.
- **`KycSubmitComponent`** — reactive form (document type/number) + a
  drag-and-drop file picker, client-side-validated against the same rules
  as `KycServiceImpl.validateKycFile` (PDF/JPG/JPEG/PNG, 10MB max) for
  instant feedback — the backend re-validates by content, not extension, so
  this is a convenience, not the real gate.
- **`KycDocumentPreviewComponent`** (`features/kyc/kyc-document-preview/`) —
  fetches the uploaded file via `GET /kyc/{id}/document` (new in backend
  v14) as a blob and renders it as an image or embedded PDF. Shared between
  the customer status view and the teller review dialog. Note it sanitizes
  the blob URL via `DomSanitizer.bypassSecurityTrustResourceUrl()` before
  binding it to `<embed src>` — Angular treats that as a resource-URL
  context and silently strips an untrusted string there (unlike `<img src>`,
  which doesn't need it).
- **`TellerKycService`** / **`TellerKycListComponent`** (`features/teller-kyc/`)
  — `/teller/kyc`, gated to `TELLER`/`ADMIN` via `roleGuard`. A table of
  pending submissions with a review dialog (document preview + verify/reject).
  **Known backend gap**: `KycResponse` only carries `userId`, no name or
  email, and there's no endpoint to join one in — the UI shows `User #<id>`
  rather than fabricate a name. Worth adding a lookup endpoint if this
  becomes a real pain point for tellers.
- **Routing/nav wiring**: sidebar has "Complete KYC" (`CUSTOMER`) and "KYC
  Review" (`TELLER`/`ADMIN`) entries; the shell's `PENDING_KYC` banner links
  to `/kyc`; `LoginComponent` sends a `PENDING_KYC` customer straight to
  `/kyc` after login instead of `/dashboard` (unless there's an explicit
  `returnUrl`) — since that's genuinely the only useful thing they can do
  until it's approved.
- **`withSilentErrors()`** (`core/interceptors/error.interceptor.ts`) — new,
  general-purpose escape hatch alongside `withIdempotencyKey()`: opts a
  request out of interceptor-level toasts entirely, for calls where an
  "error" response is actually an expected state the caller already handles
  (the KYC-status 404 being the first use of it, not the last).

## Roadmap (later phases, not built yet)

- Accounts, cards, statements (account-service) — this is what KYC
  verification actually unlocks; a `PENDING_KYC` customer should be guarded
  away from this module too once it exists, mirroring the backend's real
  enforcement (see account-service's `GatewayAuthFilter`)
- Transfers / deposits / withdrawals, with the `Idempotency-Key` interceptor
  already wired up and waiting (`withIdempotencyKey()` in
  `core/interceptors/idempotency.interceptor.ts`)
- Real-time balance updates over STOMP/SockJS (`/ws`, subscribe to
  `/user/queue/balance`) — dependencies are installed, nothing wired yet
- Loans (apply, review, EMI schedule, pay-EMI — see the CORS caveat above)
- Admin console (user/account/transaction management)
- AI assistant chat (ai-service has SSE streaming support server-side)
